# Tracker V4 research: nutrition and recipes

Research started 2026-10-03; completed 2026-10-04 (Asia/Bangkok). Filename retains the original research batch date. This is a design evidence document, not an implementation or a nutrition prescription.

## Recommendation

Prioritize a searchable meal composer with favorites, meal-specific recents and multi-add; explicit grams/serving entry; and recipe batch scaling with clear nutrition arithmetic. Follow with selective meal copying, recipe search/duplicate/tag filters, and a simple local shopping checklist. Keep photos as local visual references. Quick manual macros can reduce library clutter; automatic photo nutrition, remote AI, public food databases and cloud recipe import require a different privacy and data-quality scope and are deferred.

These priorities are an original adaptation for Tracker. Product documentation establishes that the patterns exist. User reports explain possible friction and failure modes; they do not establish feature effectiveness, prevalence of bugs, or health outcomes.

| Recipes | Structured quantity/unit/name ingredients, ordered steps, tags, notes, serving count, optional complete manual macros **per serving**, CRUD and photos. | No automatic ingredient-to-nutrient lookup. Unknown nutrition remains `null` and cannot be logged as measured macros. |

| Photos | Food/recipe owner metadata; compression and thumbnails local; library deletion keeps old nutrition snapshots and leaves gallery photos. | Reuse existing ownership and backup behavior. Do not silently turn image storage into image analysis/upload. |

## Recipe arithmetic contract for a future implementation

The following is a proposed Tracker contract, not a claim about every competitor. It uses the existing manual per-serving macro model. Ingredient nutrition is not inferred.

Let base yield be `S`, numeric ingredient quantity be `q`, and base per-serving macro vector be `p` (kcal/P/C/F). Base total is `T = S × p` when nutrition is known.

| User intention | Ingredient quantities | Batch nutrition | Nutrition per portion | Example: base 4 portions, 200g ingredient, 400 kcal/portion |
| --- | --- | --- | --- | --- |
| **Cook more/less**, target `S′` with same portion size | `q′ = q × S′ / S` | `T′ = T × S′ / S` | `p′ = p` | Cook 6: 300g ingredient, 2400 kcal batch, 400 kcal/portion |
| **Divide the same batch differently**, new yield `S′` | unchanged | `T′ = T` | `p′ = T / S′` | Divide into 8: 200g ingredient, 1600 kcal batch, 200 kcal/portion |
| **Log amount eaten**, `e` portions | unchanged | unchanged recipe | entry total `e × p` | Eat 1.5 base portions: 600 kcal in entry |
| **Log cooked grams**, measured finished weight `W`, eaten mass `w` | unchanged | unchanged recipe | entry total `T × w / W` | If 1600 kcal batch weighs 1000g, 250g logs 400 kcal |

If `p` is null, scaled amounts may display, but all nutrition remains unknown. Never treat an unknown ingredient or recipe as zero calories. Cooked weight should be explicitly measured/user-entered; sums of raw ingredient weights cannot account for evaporation. A density mapping is required to convert cups/spoons to grams. Serving labels such as bowl, scoop and egg are food-specific.

Round only for presentation. Preserve full arithmetic precision in calculation; avoid repeated scaling of already-rounded values. Do not multiply temperatures, timers, step numbers or quantities embedded in prose. If an ingredient name/step contains another amount, show the original text and an unobtrusive review note. Fraction display can be a presentation convenience without replacing the stored number.

Changing ingredients while retaining manually entered macro values needs explicit acknowledgement that macros have not been recalculated. Saving a scaled copy should produce a new recipe ID; a temporary cook-size preview should not change the base recipe. Entry snapshots must retain the exact macro basis used when saved. Recipe photo handling should continue to reference existing owner metadata without copying Blobs unnecessarily.

## Delivery order and verification implications

1. **First daily-use slice:** searchable composer, pinned foods/recipes, selected-meal recents, multi-add and selective copying. Measure taps/time with realistic repeated meals; no claim of speed improvement until tried.
2. **Portion correctness slice:** structured optional food basis; clear recipe scale/repartition/log actions; reversible preview and readable math. Verify arithmetic with known examples, decimal/fraction quantities, unknown macros and old schema backups.
3. **Cookbook slice:** recipe search over name/ingredients/tags, duplicate, optional times and cooking focus. Add conservative shopping checklist only after scale transfer is correct.
4. **Convenience slice:** one-off manual macros and local structured paste import. Preview parsed fields, retain source notes and report unsupported units. Defer autonomous suggestions about what to eat.

Relevant future checks are behavioral: selecting five items saves five once; canceled previews write nothing; stale edits are rejected; repeated copy has visible provenance; previous entries survive recipe edits/deletion; selected scale carries into shopping; missing nutrition never becomes zero; import/export retains units, favorite settings and photo ownership. This research does not add tests or production code.

## Privacy and remote-feature boundary

Food/recipe photos, private notes, diary contents and personal plan material were not uploaded during this research. Queries contained product names and general feature questions. The recommendations preserve Tracker's localStorage/IndexedDB model and existing backup safeguards.

Barcode decoding is not nutrition lookup: a local decoder can read a number, but resolving the product generally needs a data source. A hypothetical local barcode-to-user-food map is feasible; a global database is a separately scoped service. Label OCR, operating-system dictation and browser speech APIs must not be assumed local merely because their UI is on the device. Any later adoption needs verified processing behavior and a manual alternative.

Cloud AI is demonstrably a separate boundary: [FoodNoms' current policy](https://foodnoms.com/privacy) describes relaying text/link/image inputs to OpenAI. [YAZIO's help](https://help.yazio.com/hc/en-us/articles/39137901903889-What-is-the-AI-Calorie-Tracking-Feature-and-how-does-it-work) labels photo-derived nutrition as an estimate and supports correction. These sources justify deferring remote estimation for Tracker; they do not prove the exact data route of other vendors. Local pasted text/imported files can be previewed without requesting remote pages. A saved source URL should remain inert until explicitly opened.
